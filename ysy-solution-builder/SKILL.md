# ysy-solution-builder（智慧交通方案 · 准备与路由）

## 1. 本技能做什么

把「智慧交通业务场景 → 一套完整交付物」这件事，收敛成一条可复制的工作流。本技能不做具体场景的业务口径，只负责三件事：

1. **准备**：核对并装载产出交付物所需的依赖技能（文档三件套 + 读取转换类），缺则补齐；
2. **路由**：把用户提出的场景分派到对应的 `ysy-*` 领域技能；
3. **框架**：给出跨场景统一的交付框架、数值规则设计要点与原型设计准则，供各领域技能复用。

> 定位边界：改「某个场景的规则口径、页面、数据」去对应领域技能；改「交付框架、依赖技能、路由」来本技能。

## 2. 何时使用

- 用户给出一个智慧交通业务场景，要求产出一套完整交付物（需求 → 方案 → 原型 → 核心功能 → 演示清单）；
- 用户准备开工，需要先确认依赖技能是否就位、该走哪个场景技能；
- 需要一套跨场景通用的交付框架或数值规则设计参考。

## 3. 依赖技能就位（开工前一次性）

开始任何场景前，先核对依赖技能是否可用。**只认市场可装技能**——`tencent-docx` / `tencent-pptx` / `tencent-docs-sheetagent` / `tencent-docs-sheet-generation` 等是 WorkBuddy **内置插件**，随 WorkBuddy 预装、开箱即用，**不需要也不应从市场安装，更不必写进依赖清单**（市场里也搜不到这些名字，去市场装必然失败）。

需要核对/安装的是**市场可装技能**，缺失时用 `marketplace-skill-installer` 按**下面列出的精确市场名**从推荐市场搜索安装：

| 用途 | 市场技能名（精确） |
|---|---|
| PDF 读取与处理 | `pdf` |
| 文档转 Markdown（PDF / Word / PPT / 图片 OCR） | `markitdown-skill` |

**就位判据**：逐个确认上述市场技能可用；缺失时用 `marketplace-skill-installer` 按精确名装，装完复核。内置文档三件套随 WorkBuddy 自带，缺失即说明安装不完整（非市场问题）。

**运行环境与库**（生成 5 类交付物的实际依赖，开工前确认可用）：

| 交付物 | 运行环境 / 库 | 用途 |
|---|---|---|
| 需求 / 方案 docx | Python + `python-docx` | 生成 Word 文档 |
| 3 张 Visio 流程图 | Python + `vsdx` 库 | 生成并校验 vsdx 可解析 |
| 系统原型 / 演示清单 | 无需（直接写 HTML） | — |
| 系统核心功能 | Node | 运行 `test.js` 校验判定结果 |

> ⚠ 不要依赖本机自定义 / 第三方手工安装的技能（如 `docx-to-original-html`、`cnki-advanced-search`、`deep-research-pro` 等）——这些不在市场、现场机器不一定有。依赖清单只认市场可装技能。

## 4. 开工与收尾门禁（强交互，不可跳过）

**开工前必须先确认，不得直接开做**。顺序：

1. **路由确认**——向用户复述命中的场景与对应技能，请用户确认「是不是这个场景」；
2. **内容清单确认**——把本场景要产出的 5 类交付物逐项列给用户，请用户确认「就做这些、缺哪项补哪项」；
3. **需求调研前置**——完成 §12 的四层需求调研交互后，才进入生成。题目口径与技能预设不同时，以用户口径为准并回写场景技能规则表。

**阶段收尾确认（每类交付物完成后）**：产出后先自检（占位符 / 口径一致 / 可运行），再把成果要点与自检结论列给用户，**待用户确认当前阶段成果合规后再进入下一类**，不得连续自动跑完。

> 门禁判据：启动三步未逐一获用户确认，不得开始生成；任一阶段未获用户确认，不得进入下一阶段。

## 5. 场景索引与路由

七个领域技能各自绑定一个业务场景的规则口径、页面、数据模型与验收基线。按用户场景命中下表路由：

| 场景 | 技能 | 一句话定位 |
|---|---|---|
| 智慧工程建设 | `ysy-smart-construction` | 施工现场安全（人 / 机 / 环 / 进度）一体化管理 |
| 智慧试验检测 | `ysy-smart-inspection` | 试验检测机构委托受理到报告签发 |
| 基础设施养护 | `ysy-infrastructure-maintenance` | 桥隧路面病害分级与养护工单时限 |
| 质量管控 | `ysy-quality-control` | 材料报验判定与整改放行 |
| 数据分析 | `ysy-data-analysis` | 多源数据清洗与供应商评级 |
| 平台设计 | `ysy-platform-design` | 平台底座（审批 / 集成 / 安全审计） |
| 道路运输安全监管 | `ysy-road-transport-safety` | 两客一危动态监控与违规闭环处置 |

路由后，业务口径与验收基线以对应领域技能为准，本技能不再重复。

## 6. 跨场景交付框架

每个场景统一产出 **5 类交付物**，缺一不可。交付物是业务工作流的产品：

| # | 交付物 | 内容与完成判据 |
|---|---|---|
| 1 | 需求分析文档 | 用户角色分析 / 功能需求清单（含优先级）/ 数据需求 / 非功能需求；成型后交付 Word、PDF 与 **HTML 美化版** 三份 |
| 2 | 数字化解决方案 | 痛点分析 / 业务闭环设计 / 角色职责 / 规则体系 / 功能规划 / 技术架构；含 3 张 Visio 流程图（vsdx 可编辑格式，符号规范见 §14）；交付 Word、PDF 与 **HTML 美化版** 三份 |
| 3 | 系统原型 | 可演示的 HTML，覆盖核心页面，浏览器可直接打开演示，页面间可点通闭环 |
| 4 | 系统核心功能 | 实现 1—2 个核心判定功能（如自动分级判定 / 超期督办 / 重复违规识别），可运行并附说明 |
| 5 | 演示操作清单 | 单文件 HTML：把演示阶段在每个原型页上的交互动作逐条列出，每条追溯到功能需求，说明预期响应 |

**规则体系是方案的核心**：一条规则必须写清「分类 / 分级 / 判定条件 / 处置时限 / 升级督办 / 主体责任」，判定条件里的数字（阈值）要可核验，并与原型展示、代码口径三处一致。

**HTML 美化版**（第 1、2 类交付物）：在 Word 版定稿后，另存一份单文件美化 HTML（与 docx 内容一致，供浏览器直接阅读 / 打印 / 对照）。生成方式用 python-docx 按文档顺序（段落 + 表格，含嵌套）抽取后套统一样式（封面头图 + 卡片式排版 + 表格斑马纹），**不依赖 docx-to-original-html 等本机自定义技能**——现场机器只要有 python-docx 即可复现。文件命名与 docx 同名（`需求分析文档.html` / `数字化解决方案.html`），存放于对应交付物目录下。


**方案设计次序**：先定规则口径 → 再规划功能（每个功能追到规则/需求）→ 最后落页面（原型页面与功能逐条对应）。这是跨场景通用次序。

## 7. 数值规则设计要点（跨场景通用）

设计可判定、可核验的数字规则时，以下要点是业务正确性的关键（每一条都曾真实翻车）：

1. **边界必须锁两侧**：口径写「> 50%」时，"恰好 50%"必须判为不触发、"刚超过"判为触发。只测一侧等于没测。
2. **数学退化点显式处理**：标准差为 0 时 `|x−μ|>3σ` 会退化成"全部离群"；零样本不等于达标（合格率红线 90% 时空样本按 0 算）；除零、空数组、空读数一律先走"无有效读数"分支。
3. **时限先钉死计时单位**：工作日 ≠ 自然日。"3 个工作日"跨周末可能对应 4—6 个自然日，工作日记数要跳过周六日。
4. **判定顺序按严重性降序**：多条件命中时先判的规则胜出，须按严重性从高到低排列分支，避免后判覆盖前判。
5. **明细顺序稳定**：明细列表按数据原始顺序输出并写进约定，避免顺序漂移。

## 8. 原型设计准则（跨场景通用）

原型是**回答设计问题的可运行演示**，不是最终产品——它验证「规则口径与交互闭环是否成立」。设计时遵守：

1. **先答问题再谈页面**：从「要回答哪个设计问题」出发——是验证判定逻辑，还是验证交互闭环；分支不同，原型侧重不同。
2. **单文件、可一键运行**：一个浏览器直接打开的 HTML，无需构建与安装即可演示。
3. **无持久化**：状态驻留内存，不依赖数据库；持久化是原型要验证的东西，不是它依赖的东西。
4. **展示状态**：每次操作后把相关状态（判定结果 / 时限 / 计数）渲染出来，让人看到变化。
5. **跳过打磨**：不做多余错误处理与抽象，点到为止，目的是快速验证。
6. **完成即归档**：验证通过的决策折回正式交付物；原型本身作为「回答过的问题」留存，页面上注明它回答了什么、结论是什么。

**原型完成判据**：能点通闭环、状态联动正确、规则口径与「数值规则设计要点」一致、每条功能需求都有对应页面。

## 9. 质量与合规要点

- **不留占位符**：交付物里出现「— / TODO / __XX__」等于宣称没做完，产出前做一遍占位符残留自检。
- **口径可溯源**：规则阈值与时限要有来源——题面给定值、引用标准号（写明标准号与条款号）、或自定口径（显式标注）。禁止凭空编造标准号，也禁止把自定值伪装成标准值。
- **不编造业务事实**：不添加样例里没有的业务术语 / 字段 / 数据。
- **规则与展示一致**：方案规则表数字、原型展示、代码阈值三者同口径，改一处必须同步另两处。

## 10. 维护约定

- 领域技能 `version` 只在 frontmatter 写一次；每轮审查优化后统一升版。
- 各领域技能的「待审查清单」即该场景的优化 backlog，逐项勾掉后同步更新「已知坑」。
- 改「交付框架 / 依赖清单 / 路由表」来本技能；改「规则口径 / 页面 / 数据」去对应领域技能，避免两处漂移。

## 11. 需求分析内容框架（跨场景通用）

需求分析文档不是散文，是**可核验的需求清单**。功能 / 数据 / 非功能三类需求各写什么、怎样算完整：

| 需求类别 | 写什么 | 完成判据 |
|---|---|---|
| 功能需求 | 按「角色 × 业务动作」枚举，每个功能追到一条痛点 / 规则，标注优先级 | 每个角色至少 1 个功能；每个功能可回到痛点或规则 |
| 数据需求 | 每个功能的入参（字段 / 单位 / 口径）、出参、数据来源（题面值 / 标准号 / 自定） | 入参与规则表同口径；来源可追溯、不编造 |
| 非功能需求 | 时效（时限口径：工作日 / 自然日、分钟 / 天）、并发 / 性能、安全（权限 / 审计）、可复现性 | 时限与规则表一致；安全与审计口径明确 |

**三类齐备判据**：功能需求覆盖全部规则触发点；数据需求与规则表、原型表单、代码入参四方一致；非功能需求含时效与安全两条主线。

## 12. 需求调研追问（跨场景通用 · 借鉴 grilling · 生成前置必答）

**生成任何交付物之前，必须先完成本需求调研交互，不得跳过或用技能预设直接开做**——实际题目口径几乎必然与预设不同，跳过调研等于把预设当答案，产物必然偏题。对每个场景按四层推进，每层达成完成判据后进入下一层：

1. **角色与场景层**——列出全部角色与各自业务动作，连成闭环。
   完成判据：每角色 ≥1 动作，动作连成闭环。
2. **痛点层**——从现状归纳真实痛点，每条写「现象 → 后果」。
   完成判据：每条痛点对应 ≥1 功能需求。
3. **规则口径层**——把本场景判定规则逐条钉死（分类 / 分级 / 判定条件 / 时限 / 边界两侧）。
   完成判据：每条规则可判定、可核验，边界两侧（恰好 N / 刚超过 N）都有结果。
4. **来源追溯层**——每条需求与规则追到来源：业务痛点、标准号（写明标准号与条款号）、题面给定值；自定口径显式标注。
   完成判据：无来源的需求为零；不编造业务事实与标准号。

**给用户推荐答案**：每层先给出本场景的默认口径（见场景技能「规则体系」），请用户确认或修订，而不是让用户从零描述。用户修订后以用户口径为准，并回写场景技能规则表。

## 13. 核心功能实现路径（跨场景通用 · 技术路线）

核心功能 = 把**规则表翻译成可运行判定**。实现路径是**技术路线**，不依赖任何本地目录 / 脚本（现场目录位置无法确定，禁止硬编码路径）：

1. **规则表 → 引擎函数**：规则表每行对应一个判定函数，阈值、边界、单位与规则表逐字一致。
2. **引擎函数 → 接口层**：引擎函数封装成接口，供页面调用；接口层必须被真实调用，不得直连引擎。
3. **接口层 → 页面**：演示页所有操作走接口层，页面与功能逐条对应。
4. **完成判据**：每条功能可运行、输出与规则表逐字一致、分支全覆盖、边界值正确；不依赖特定文件路径。

## 14. Visio 流程图绘制规范（跨场景通用）

交付物是 **Visio 流程图**（不是泳道图）。图形必须用标准流程图符号，流程准确：

| 符号 | 含义 |
|---|---|
| 椭圆 / 圆角矩形 | 开始 / 结束 |
| 矩形 | 处理过程 |
| 菱形 | 判断 / 决策 |
| 箭头 | 流程流向 |

绘制要求：
- 每张图表达一个完整业务闭环，起止用椭圆 / 圆角矩形；
- 判断点用菱形，分支标注「是 / 否」与条件；
- 关键环节可标注负责角色（文字标注，非泳道）；
- 与方案「流程图说明」章节一一对应；
- 产出可编辑的 vsdx 格式。

**完成判据**：符号规范、闭环完整、判断分支清晰、与方案章节对应、vsdx 可解析。
